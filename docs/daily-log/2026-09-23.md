# 2026-09-23 — Day 29

**Focus:** The one case yesterday's runbook marked as not drilled: API Priority and Fairness with
`limitResponse: Queue`. Rejection announces itself with a 429. Queueing says nothing at all.

**Studied:** APF's queueing parameters (`queues`, `handSize`, `queueLengthLimit`), what happens when
a queue overflows, which FlowSchema actually serves `/readyz`, and how `for:` windows behave when the
condition underneath them flaps.

**Did:** Hypotheses first, as usual. H1: queueing produces delay and no errors, so the day-28 fix
generalises unchanged. H2: a request held past the server's own timeout comes back as text nothing
classifies, and becomes a 502. H3: the probe is fired once per timed-out call, which is a burst aimed
at a server already over capacity. H4: throttled releases land under `reason="deadline"` rather than
`busy`. H5: `Retry-After: 5` stays a guess. H6: the stalled-server and frozen-node cases must still
read as unreachable.

A throwaway cluster, ten releases, the orchestrator as its own service account again, three seats,
and a queue instead of a rejection. Getting the drill to bite took two rounds: 40 threads against an
empty namespace changed nothing measurable, and when I added 60 ballast secrets and 160 more threads
the queue overflowed and the server started rejecting — drill 9's incident, arriving through drill
10's door. Widening the queue to 200 put it back on the path I meant to test: 20,000 requests served,
not one refusal.

H1 was wrong in the way that mattered. With nothing failing, `nf_cluster_busy` stayed 0, the cluster
read as reachable, and eight to ten of ten releases went unreported for `reason="deadline"` — which
is drill 7's incident, whose runbook is about the orchestrator having too much to do. And some scrapes
reported `nf_cluster_reachable 0` outright, the page for a dead control plane, while the
orchestrator's own `/readyz` route answered `200 reachable` seconds later.

H4 held. H2 did not: our 3s bound kills a call long before the server's 32s timeout can produce any
text, so that branch is unreachable for reads by construction. H3 held and is fixed.

**Got stuck on:** why the probe was slow. Day 28 rests on `/readyz` being served outside the
throttled level, and it is — the API server's own dispatch counters show the probe landing on the
built-in `probes` FlowSchema every time, never on the drill's. It was still taking 0.45 to 3.58
seconds against 0.06 idle, because a server saturated with expensive lists is slow on every path it
serves. Being exempt from flow control is not the same as being fast. That is the whole of finding 2,
and it means "the probe did not answer in 0.75s" was never the test for "the cluster is gone" that I
took it for yesterday.

So the fix has two halves. Reachability now takes either of two witnesses — the probe answering, or
any other call having completed in the last 30 seconds — because the second one survives exactly the
conditions that break the first. And the probe's *duration* became a measurement in its own right,
timed once per scrape on a thread beside the work, published as `nf_cluster_probe_seconds`, and read
as back-pressure above 0.5s even when every release was read successfully. That last part is what
makes an incident visible while nothing is failing.

Under the same load afterwards: reachable 1 throughout, busy on 94.7% of scrapes,
`ClusterThrottlingOrchestrator` firing at 08:22:48Z, `ClusterUnreachable` never active. Then the
regressions — drill 7's stalled TLS server still unreachable at the same cost, a paused node
unreachable, recovery clean within 8 seconds.

Two more findings came out of the day's own changes. The alert would not have fired at moderate load:
`nf_cluster_busy` flapped around its threshold and `== 1 for 2m` needs an unbroken run, so the rule
now asks what share of the window was busy. And the guard that stops unit tests reaching a real
cluster turned out to be blind to threads — the scrape probes on one now, and pytest downgrades an
exception raised there to a warning. The guard that exists because a check quietly stopped checking
had the same hole in it.

**Learned:** Exempt is not fast, and "it didn't answer in time" is not "it isn't there". Every
diagnosis I have written so far reads a single signal and names an incident from it; two drills in a
row have now broken one of those signals while the incident stayed the same. A second witness is
cheap. The other half is that an incident which produces no errors needs a measurement that exists
when nothing goes wrong — the probe's duration was already being paid for, and until today it was
thrown away.
