# 2026-08-26 — Day 13

**Focus:** Answer the one drill finding still open — what a *stable* lifecycle state means — and
prove the answer with real alert rules rather than an argument.

**Studied:** Prometheus custom collectors, which produce metrics at scrape time instead of caching a
value the application updated earlier, and `for:` in alerting rules — the window a condition must
hold across every evaluation before an alert leaves `pending`. Also, unexpectedly, Kubernetes
server-side apply field managers, after Helm refused an upgrade because `kubectl` owned a field.
Sources: https://prometheus.github.io/client_python/collector/custom/,
https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/,
https://kubernetes.io/docs/reference/using-api/server-side-apply/

**Did myself:** Decided not to debounce in the application. The endpoint keeps answering "what is
true right now"; stability gets defined per alert, in `for:`, by whoever owns the alerting. Wrote
that up as ADR-0007 with the alternatives I rejected, including a hysteresis rule inside
`derive_state` and using the Deployment's `Progressing` condition — the latter would not have caught
drill 1's flap at all, since deleting pods does not change the Deployment's generation.

Added `LifecycleCollector` to `orchestrator/metrics.py`: a custom collector that reconciles every
Helm release at scrape time and emits `nf_deployment_state{release,state}` as 0/1 per state, plus
`nf_deployment_desired_replicas`, `nf_deployment_ready_replicas` and `nf_cluster_reachable`. That
closes the ADR-0005 gap where nothing observed a deployment nobody was polling — the scrape interval
is now the poll interval, without a background loop. A scrape that cannot reach the cluster emits
`nf_cluster_reachable 0` and no release series at all, because an unreachable cluster must not look
like an empty one; that is drill 2's lesson applied in a new place.

Then verified it against a real Prometheus with four rules loaded. A 57-second shortfall (Deployment
scaled to 1 outside Helm) held `NFNotInstantiated` and `NFReplicaShortfall` at `pending` for its
whole duration and cleared without either firing. A sustained failure — same release upgraded to a
nonexistent image tag — went `FAILED` at 13:46:50, `pending` at 13:47:01, and `firing` at 13:47:53,
about 60s later, matching `for: 1m`. Four new tests, 55 in total, `ruff check .` clean.

**Got stuck on:** The thing that made the day. Restoring the replica count at the end of the first
experiment, I resubmitted the intent through the API and got a `502`, and `NFFailed` appeared in an
experiment where only shortfall alerts were expected. Helm 4 applies with server-side apply, and
`kubectl scale` had taken ownership of `.spec.replicas`, so the upgrade hit
`conflict with "kubectl.exe" with subresource "scale"`. Worse, the failed upgrade left the release
`status: failed`, and `derive_state` maps that straight to `FAILED` — so a workload that was still
serving went from an accurate `INSTANTIATING` with 1 of 2 ready to `FAILED`, with nothing about the
workload having changed. Retrying appended more failed revisions instead of clearing it.
`helm upgrade --force-conflicts` repairs it in one command, and the deploy engine does not pass that
flag.

Reproduced it deliberately and wrote it up as drill 3. Whether the orchestrator should pass
`--force-conflicts` itself is left open in an action item rather than patched today: always passing
it means silently overriding any other controller that touches these Deployments, including an
autoscaler doing its job, and that deserves its own ADR.

**Learned:** The runbook I wrote on Day 12 told operators to do exactly the thing that breaks. Step 6
said resubmitting the intent would undo drift, and it was written from a command I really had run —
but during a drill where nothing had touched the Deployment, so it succeeded for reasons that had
nothing to do with repairing drift. Day 11's rule was "only document steps you actually ran". That
is necessary and not sufficient: a step can be genuinely executed and still be documented for the
wrong situation. Added that as a corollary to the drill process.

The other one: the alerting rules earned their keep before they were finished. `NFFailed` showing up
in an experiment that had nothing to do with failure is what surfaced the bug. Instrumentation is
worth having partly because it notices things the person watching is not looking for.
