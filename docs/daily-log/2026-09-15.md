# 2026-09-15 — Day 26

**Focus:** Day 25 raised the scrape's ceiling without lowering its slope, and ADR-0014 admitted the
ceiling had never been measured. Measure where the time goes, cut the calls that are not needed, and
prove the answers did not change.

**Studied:** What one helm or kubectl call actually costs on this host, whether `helm status` says
anything `helm history` does not, and `helm list --help` in Helm 4 — where `--all` no longer exists,
every status is listed by default, and the result stops at 256 unless paged.

**Did:** Wrote three hypotheses down first. H1: call count sets the slope, not API latency. H2:
`helm status` is redundant with the newest `helm history` entry. H3: one `kubectl get pods -l app`
grouped by label gives each release exactly what its own selector does.

H1, ten runs of each call on a 20-release kind cluster: every API call 94-110ms; `helm version` and
`kubectl version --client`, which never touch the API, 63ms. Two thirds of every call is starting a
process. One pod listing for all releases cost 109ms against 94ms for one release's.

H2 needed the states to exist, so I made them: a drift conflict for a failed upgrade, a short
`--wait` on a missing image for a failed first install, and `timeout 8` around `--wait` installs and
upgrades to leave `pending-install` and `pending-upgrade`. Status and history agreed in all of them,
and for an absent release both fail with the same `release: not found`. My first attempt at a failed
install — clashing with an existing Deployment — failed before Helm wrote any record, so it tested
nothing, and I had to find a way to fail *after* the record exists.

Then the change: status read from history, and the collector lists every pod once and hands each
release its share. `1 + 4N` calls per scrape became `2 + 2N`. The check that mattered was running the
saved copy of the old reconciler beside the new one on the same cluster, 22 releases plus an absent
name, three rounds, comparing every field: zero differences, with all four lifecycle states and all
four operation states in the set. 87 subprocesses became 44.

With the budget lifted to see the real cost: 60 releases, 8 workers, 4.28s before and 2.05s after.
Against Prometheus at default settings, main's build pinned every scrape at the 4.0s budget with 4
releases unreported; this branch scraped all 60 in about 2.0s — and the three `NFFailed` alerts that
fired were the three releases I had broken on purpose, which could only fire because they had series.

The `--help` read turned up the 256 cap. A release past it would have had no series and no
`nf_release_reported`, so the alert built yesterday to name unmonitored releases could not have named
it. `list_releases` pages now; on real helm, pages of 5, 7, 11 and 22 returned the same 22 names as
one page, and a plain `--max 7` returned 7 of 22 without a word.

**Got stuck on:** A test that kept passing for the wrong reason. After the refactor, the 503 test
still faked `helm_release_status`, which `reconcile` no longer calls — so it ran real helm against my
stopped local cluster, got a real 503, and passed. It would pass the same way on any machine without
a cluster. I only noticed because I read why each test still passed instead of being relieved that
they did. Added an autouse guard that fails any unit test running helm or kubectl for real, showed it
catches that test, then ran it against main's untouched tests: all 147 clean, so this one was mine
and caught before it was committed.

Smaller: a Python edit wrote CRLF line endings into `reconciler.py` — the same Windows default as day
24's cp1252, different byte. And a "which build is serving" check I wrote printed `True`
unconditionally; replaced it with importing the module from the same directory and checking for a
function only the new code has.

At the end the persistent cluster would not start: `bind: forbidden by its access permissions` on
port 64114. Windows had reserved 64028-64127 after Docker Desktop restarted. The fix restarts a system
service as administrator, so it is written into the control-plane runbook as not drilled and left to
run by hand.

**Learned:** Measure the floor before optimising the query. The instinct was that API latency was the
cost; the 63ms of a call that never reaches the API said otherwise, and it changed the fix from
"faster calls" to "fewer calls".

And a refactor is the moment tests are most likely to pass without testing anything, because the
seams they faked have moved. Green after a refactor is a question — which fake did each test go
through? — not an answer. The guard turns that question into a failure.
