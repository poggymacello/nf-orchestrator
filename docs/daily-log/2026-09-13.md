# 2026-09-13 — Day 23

**Focus:** Stop fixing documentation drift by hand, and give drill 5 the runbook every
other drill got.

**Studied:** Nothing new. This was about making a lesson from day 21 enforceable instead
of remembered.

**Did myself:** On day 21 the publish pass fixed a README claiming 74 unit tests when there
were 122. Today it claimed **122 when there were 128** — three days later, the same kind of
number, in the same sentence. A second manual pass would rot on the same schedule, so I
wrote `tests/test_doc_claims.py` instead. It reads the front-door documents and fails the
build when a stated number stops matching the repository: unit tests, end-to-end tests,
ADRs, and CI jobs in two places.

Each check requires the claim to be *present*. A reworded sentence that no longer matches
fails rather than passing silently — the fail-closed rule from the banned-terms gate on day
17, for the same reason. There is a test for that property directly.

The unit-test count is taken by counting `def test_` in the source rather than by running
pytest, because a test that ran the suite to count itself would be circular. That is only
exact while nothing is parametrized, so another test asserts that rather than assuming it.

Then drill 5's runbook, `runbooks/node-under-disk-pressure.md`, written from the commands
run on day 22. Two steps it needs — finding an unknown disk consumer, and clearing evicted
pods from a real release — were not run during the drill, so they are marked **(not
drilled)** instead of presented as tested. The operations page used to say every runbook
command had been run against the cluster; that is no longer true, so it now says what the
marking means. 135 tests pass.

**Got stuck on:** The new test caught two bugs in itself before it caught anything in the
docs.

My helper for counting tests was called `test_functions`. Pytest collects anything starting
with `test_`, so it tried to run the helper as a test and errored on a missing fixture —
and the regex counting `def test_` would have counted the helper too, making every future
count wrong by one. A test named badly enough to be mistaken for a test, inside a test that
counts tests.

The other one would have broken CI. The test reads `ci.yaml` with PyYAML, which imported
fine locally. `pip show pyyaml` reported **`Required-by:` empty** — nothing in the project
depends on it. It was in this virtualenv only because I had once installed it by hand to
validate some YAML. In CI, `pip install -e ".[dev]"` would not have brought it, and the test
would have passed here and failed with `ImportError` there. Declared it in the dev
dependencies. That is the fourth local-versus-CI difference in this project, and the first
one I caught before pushing rather than after.

Writing the runbook also turned up a stale line in the *other* runbook: step 5 still said
what counts as a stable state for alerting "is still an open question (drill 1, action item
4)". ADR-0007 answered it on day 13 — ten days of a runbook describing a question as open
that had been closed.

**Learned:** Day 21 concluded that status prose rots and should be checked mechanically.
I wrote that down and then did not do it, and the drift came back in three days. A lesson
recorded as prose has the same half-life as the prose it is about. The version that holds
is the one that fails a build.

The runbook marking is a smaller version of the same idea. "Every command here was run
during the drill" was true for three runbooks and would have been false for the fourth the
moment I wrote it. Rather than stretch the claim or drop the untested steps, the claim got
narrower and more exact: drilled unless marked. A general statement about a set is a claim
that has to be re-checked every time the set grows.
