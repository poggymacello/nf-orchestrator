**Did myself:** Read `.github/workflows/ci.yaml` in full. It has exactly one job, `lint-test`:
triggered on push to `main` and on pull requests, runs on `ubuntu-latest`, installs the repo with
`pip install -e ".[dev]"`, then `ruff check .` and `pytest`. That is the entire real CI surface.
`CONTRIBUTING.md` describes Gitleaks and a banned-terms grep as "Enforced in CI" — neither exists
in `.github/workflows/`. Flagging this rather than fixing it silently; it's a docs/reality gap that
predates today, not something to paper over.

Pushed a branch (`ci-fail-probe`) with a throwaway file containing unused imports, meant to break
CI. First push produced no run at all — the workflow only triggers `push` on `main`, not on other
branches; only `pull_request` fires for a feature branch. Opened a throwaway PR, which triggered
the real run. It failed: job `lint-test`, step `Run ruff check .`, `F401 'os' imported but unused`,
exit code 1. Closed the PR and deleted the branch, both locally and on origin. `git branch -a`
confirms only `main` remains.

**Got stuck on:** The exercise asked me to fail CI "on the leak-scrub check," but no such check
exists in this repo yet — only lint+test does. Used the real gate instead rather than fabricate a
job that isn't there.

**Learned:** `push: branches: [main]` in a workflow trigger means pushes to any other branch are
silent — no run, no failure, nothing. A PR against `main` is what actually exercises the
`pull_request` trigger. Easy to assume "pushed a branch" means "CI ran."
