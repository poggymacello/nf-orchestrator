# 2026-07-16 — Day 4

**Focus:** Deploy a workload with Helm onto kind by hand and watch it reach Running.

**Studied:** kind's architecture (cluster-in-Docker) and Helm's release/upgrade model.
Sources: https://kind.sigs.k8s.io/docs/user/quick-start/, https://helm.sh/docs/intro/using_helm/

**Did myself:** No stand-in NF chart exists yet (M2), so wrote a minimal scratch chart
(`Chart.yaml`, `values.yaml`, one Deployment template) deploying `nginx` as a placeholder. Reused
the existing M0 kind cluster rather than creating a new one. `helm install` → pod went
`ContainerCreating` → `Running` in 13s. `helm upgrade --set replicaCount=2` brought up a second
pod without touching any manifest by hand. `helm uninstall` removed the release cleanly.

**Got stuck on:** Deliberately pointed the chart at a nonexistent image
(`stand-in-nf-app:local`) to see what breaks. `helm upgrade` reported success regardless — it only
confirms the manifest applied, not that the workload is healthy. The pod actually went
`ErrImagePull` → `ImagePullBackOff`; `kubectl describe pod` showed kubelet trying to resolve the
image against Docker Hub and failing, since kind nodes don't share the host's local image cache.
Fixed by reverting to the known-good `nginx` image; the real fix for an actual local image is
`kind load docker-image`, not yet exercised since nothing is built to load at this milestone.

**Learned:** `helm upgrade` succeeding tells you the manifest was applied, not that the pod is
healthy — those are two separate facts, and only `kubectl get pods` confirms the second one.

**Doc updated:** docs/learning-notes/helm-and-kind.md.

**Time:** ~60 min.
