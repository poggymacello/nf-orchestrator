# 2026-08-27 — Day 14

**Focus:** Decide drill 3's open question — whether the deploy engine should force server-side apply
conflicts — and implement whatever the decision turns out to be.

**Studied:** Kubernetes server-side apply field managers in more detail: that `kubectl scale` writes
through the `scale` subresource and registers as a manager for `.spec.replicas`, that `--show-managed-fields`
lets you see who owns what, and that `--force-conflicts` is a transfer of ownership rather than a
retry. Also Helm's revision model — `helm history --output json` carries a per-revision status, and
`helm get values --revision N` reads that revision specifically.
Sources: https://kubernetes.io/docs/reference/using-api/server-side-apply/,
https://helm.sh/docs/helm/helm_history/

**Did myself:** Decided the deploy path never forces. Forcing means overriding whatever else was
writing to that field, and `POST /deployments` cannot know whether that is a mistake or an
autoscaler doing its job. Instead a conflict is now its own exception, `ClusterConflict`, mapped to
`409` with a detail that says resubmitting will not help and names the way out — a third code
alongside `503` unreachable and `502` refused, for a third kind of problem.

Added `POST /deployments/{name}/repair`, which takes the same intent body and applies it with
`--force-conflicts`, returning `"forced": true`. It takes a body rather than restoring "the intent on
file" deliberately: after a failed upgrade there are two recorded intents, and picking for the caller
is exactly the ambiguity that caused the second bug below. Repairs get their own counter,
`deployment_repairs_total`, because how often something else is fighting us for these fields is worth
knowing separately from deploy volume.

Verified the whole loop on the cluster: deploy 2 replicas, `kubectl scale` to 1, `GET` shows
`desired=2 ready=1`, plain resubmit returns `409`, repair returns 200 with revision 3, `GET` shows
`INSTANTIATED 2/2`. Name mismatch on the repair path returns 400. 66 tests, `ruff check .` clean,
cluster left empty.

**Got stuck on:** Not stuck exactly — caught something on the way in. Before writing any code I
checked what `helm get values` returns for a release whose latest revision failed, expecting to reuse
it in the repair path. It returns the **failed** revision's values. Which means `desired_replicas`,
written on day 12 and the whole basis of ADR-0006's `INSTANTIATED`, had been reading an intent the
cluster rejected. Set it up so the two revisions carried different values and it was unmistakable:
release running revision 1 at 2 replicas in `dev`, failed revision 2 asking for 5 in `staging`, and
the orchestrator reporting `desired_replicas: 5`.

Fixed by reading the last revision whose status is `deployed` — `last_deployed_revision()` off
`helm history --output json`, then `helm get values --revision N --all`. A release where nothing ever
deployed has no intent in effect, so the desired count is 0. Post-fix the same setup reports 2 while
Helm's own view still says 5.

**Learned:** Drill 3's finding and this bug are one confusion wearing two hats: **what was submitted
is not what is in effect.** Helm records both and its most convenient accessor returns the first. I
built ADR-0006 on that accessor without asking which of the two it answered, because in every case I
had tested they were the same value — the failed-revision case only exists after something goes
wrong, which is precisely when the state report matters most.

That is the third time in this milestone that a bug lived in the gap between two things that are
usually equal: pod phase versus container readiness, release-absent versus cluster-unreachable, and
now submitted versus applied. The pattern worth remembering is that a convenience accessor collapsing
two concepts is fine right up until the two diverge, and they only diverge during incidents.

The other thing: I found this by checking a helm behaviour I was about to depend on, rather than by
running the system. Fifteen seconds of "what does this actually return" before writing the code, and
it happened to catch a live bug in code written two days earlier.
