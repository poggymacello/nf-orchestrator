# 2026-09-12 — Day 22

**Focus:** Run the disk drill that was abandoned on day 11, because it is the last open
item in the project that does not need something I do not have.

**Studied:** kind's `kubeadmConfigPatches` for kubelet configuration, and what kubelet
actually does above an eviction threshold — taint the node
`node.kubernetes.io/disk-pressure:NoSchedule`, evict pods, and leave the evicted records
behind rather than deleting them.
Sources: https://kind.sigs.k8s.io/docs/user/configuration/,
https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/

**Did myself:** Day 11 abandoned this drill for two reasons and only one was fixable by
configuration. kind ships `evictionHard` at `0%`, which switches eviction off — a
`kubeadmConfigPatches` block turns it back on. The other reason stood: the node filesystem
is the host's, with 843 GiB free, so crossing a conventional 10%-available threshold means
writing something like 760 GiB to a laptop.

So I calibrated the threshold to the disk instead of the disk to the threshold.
`nodefs.available: "840Gi"` leaves about 3 GiB of headroom, and a bounded 5 GiB write
crosses it. Above the line kubelet behaves identically either way; only the arithmetic to
get there is different, and `rm` reverses it.

Ran it on a throwaway cluster so the persistent one every milestone has reused was never
at risk — which needed `KUBE_CONTEXT` to stop being a hardcoded constant. It reads
`NF_KUBE_CONTEXT` now, with the old value as the default.

Two findings, both fixed, both written up in
[drill 5](../operations/postmortems/2026-09-12-drill-5-disk-pressure-and-eviction.md). 128
tests pass, the drill cluster is deleted, the persistent one is untouched.

**Got stuck on:** The second finding is the one worth keeping, and I nearly missed it by
stopping the drill too early.

The incident half went as designed: DiskPressure at 18:38:27, twelve pods for a two-replica
intent, orchestrator correctly `FAILED`. The reason was discarded — `{"phase": "Failed",
"reason": null}` twelve times while Kubernetes knew every one said `Evicted` — because
`pod_states` reads the reason from a container's `waiting` block and an evicted pod never
started a container. One-line fallback to the pod-level `status.reason`, fixed.

Then I removed the ballast and watched the recovery, mostly as a courtesy to leave the
cluster tidy. DiskPressure cleared at 18:42:04. The cluster was back to 2/2 Running by
18:42:25. **The orchestrator reported `FAILED` at 18:42:25, at 18:43, at 18:44, and at
18:45**, and would have gone on reporting it until somebody deleted the evicted pods by
hand.

Kubernetes does not delete evicted pods. They sit there as `phase: Failed` with no
`deletionTimestamp`, so `pod_states` included all eight, and ADR-0009's rule — *any
non-terminating pod in a terminal phase means the workload stopped and was not replaced* —
fired on them permanently. `derive_state` now partitions live pods from terminal ones: the
intent being satisfied by the live pods wins, and a terminal pod is a failure only when it
is not. I checked that against every earlier drill's shape before shipping it, because the
rule I was changing was itself a fix.

Also caught myself twice reading a stale measurement. `pkill -f uvicorn` does not reach a
Windows python.exe from Git Bash, so the "fix didn't work" I was about to write up was the
old server still holding port 8000. Found it with `netstat -ano` and `taskkill`. That is
the second time in five days — day 18 had a `make` exit code that was actually `grep`'s.

**Learned:** The rule drill 5 broke was added on day 15 to close drill 1's finding 2, and
it was correct for that case. A pod that exited and was not replaced really does mean
failure. An evicted pod sitting beside two healthy replacements does not, and nothing
between day 15 and today exercised the difference, because every drill in between was
about a different failure.

So a fix can be right for the case it was written for and wrong for the next one, and the
only thing that finds that out is a drill which is not a re-run of the last drill. That is
a better argument for varying the drills than "coverage" is.

The smaller one: I almost stopped after the incident half. The incident behaviour was
correct and the reason fix was in hand, and it would have felt like a complete drill. The
serious finding was in the *recovery*, which I only watched because I was tidying up. A
drill that stops when the system starts working again tests half of what matters.
