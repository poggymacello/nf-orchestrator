# 2026-07-22 — Day 8

**Focus:** Build the M2 deploy engine, prove a validated intent reaches a Running pod on kind, and
document it from real output.

**Studied:** Helm values and how `upgrade --install` handles a release that may or may not exist,
and Helm's release-name constraints.
Sources: https://helm.sh/docs/chart_template_guide/values_files/,
https://helm.sh/docs/helm/helm_upgrade/

**Did myself:** M2 did not exist at the start of the day. Wrote `charts/stand-in-nf`, a chart with
`replicaCount`, `environment`, and an image default, and `orchestrator/deploy.py`, which renders
values from the M1 `Intent` and calls `helm upgrade --install` against the kind cluster. Added
`POST /deployments`, which validates the body with the same M1 model and then deploys it.

Posted `{"name":"sample-nf","replicas":2,"environment":"dev"}` and got `201` with
`{"release":"sample-nf","status":"deployed","revision":1,"values":{"replicaCount":2,"environment":"dev"}}`.
`helm get values` showed the two rendered values, `helm status` reported `STATUS: deployed`,
`REVISION: 1`, and `kubectl get pods -l app=sample-nf -L environment` showed two pods `1/1
Running` carrying `dev` as a label. Resent the same intent with `replicas: 3`: revision 2, a third
pod, and `rollout status` reported a successful rollout, so the mapping drives the cluster rather
than a fixed manifest. Torn down with `helm uninstall`, leaving the persistent M0 cluster up.
Eighteen tests pass and `ruff check .` is clean; the mapping is tested as a pure function and the
Helm call is monkeypatched, since CI has no cluster.

**Got stuck on:** A 60-character intent name passed M1 validation with `200` and then failed inside
Helm with `release name is invalid`. The M1 schema capped `name` at 63, the RFC 1123 label limit,
but Helm caps release names at 53. The engine surfaced it correctly as a `502`, but the rejection
belonged at the API boundary, so I lowered `max_length` to 53 in the model. The published schema
moved with it because `/intents/schema` is generated from that model, and ADR-0003 was corrected
since it stated 63.

**Learned:** `upgrade --install` is what makes an intent-driven API work. A caller declares desired
state and should not have to know whether they have declared it before; plain `helm install` would
turn the second submission of an intent into a name-collision error. Separately, a contract written
before the thing that consumes it carries untested limits. The 63-character cap looked correct for
a Kubernetes name and was wrong for a Helm release name, and only a real deploy showed it.
