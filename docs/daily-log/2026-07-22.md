# 2026-07-22 — Day 7

**Focus:** Build the M1 intent-validation endpoint, prove it by running it, and document it from
what it actually returned.

**Studied:** Pydantic v2 strict mode versus its default lax coercion, and JSON Schema generation
from a model.
Sources: https://docs.pydantic.dev/latest/concepts/strict_mode/,
https://docs.pydantic.dev/latest/concepts/json_schema/

**Did myself:** M1 did not exist at the start of the day. `orchestrator/` served only `/healthz`,
and the only intent validation in the repo was the Day-3 standalone script. Wrote the `Intent`
model (`name` with an RFC 1123 pattern, `replicas` 1-10, `environment` as a three-value literal,
unknown fields forbidden) and two routes: `POST /intents/validate` and `GET /intents/schema`, the
latter generated from the model so the published schema cannot drift from the enforcing code.
Pointed the Day-3 probe script at the same model so there is one definition of the contract.

Ran the app with `uvicorn orchestrator:app --port 8000` and exercised it with curl. Valid intent:
`200` with `{"valid":true,"intent":{"name":"sample-nf","replicas":2,"environment":"dev"}}`. Three
rejections, all `422`, each with a one-entry `detail` array carrying `type`/`loc`/`msg`/`input`:
missing `replicas` gives `type: "missing"`, `"replicas": "two"` gives `int_type`,
`"environment": "production"` gives `literal_error` with `ctx.expected` listing the three allowed
values. The `name` pattern rejects `"Sample_NF"` with `string_pattern_mismatch`. Nine tests pass
and `ruff check .` is clean.

**Got stuck on:** Cross-checked the schema at `/intents/schema` against the endpoint using the
`jsonschema` library and found they disagreed: `"replicas": "3"` was accepted by the endpoint
(`200`) and rejected by its own published schema. Pydantic's default lax mode coerces a numeric
string to an integer. Fixed with `ConfigDict(strict=True)`, which then looked like it had not
worked, because `uvicorn --reload` never picked up the edit and the worker was still running the
old model. Calling `Intent.model_validate` directly in a shell rejected `"3"` while the HTTP
endpoint still accepted it, which is what gave the stale process away. Restarting uvicorn produced
the expected `422`.

**Learned:** A generated JSON Schema and a lax pydantic model describe two different contracts. The
schema says `"type": "integer"`, the endpoint accepts `"3"`, and nothing warns about the gap. If
the schema is published, strict mode is what makes the published document true. Also worth
remembering that a fix which "does not work" may be a fix the server never loaded.
