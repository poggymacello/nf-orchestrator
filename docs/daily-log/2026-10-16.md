# 2026-10-16 — Day 34

**Focus:** Two things. First, the last host failures day 33 hadn't drilled: a tool that isn't
installed, and a `fork` that fails in Python itself. Second, the documentation as a whole. It had
grown drill by drill for a month and had no reference pages: nowhere to look up a setting, a status
code, a metric or an alert without reading the code or a postmortem.

**Studied:** How Python reports spawn failures (`FileNotFoundError`, `BlockingIOError`), what
Kubernetes and Alertmanager expect from readiness and `runbook_url`, and Keep a Changelog.

**Did:** Hypotheses first. H1: both failures make the scrape report a healthy cluster unreachable,
because since day 12 any `OSError` at spawn has been grouped with an outage. H2: the routes answer
bare 500s. H3: `/readyz` says "too overloaded to tell" about a missing tool.

The scratchpad had been cleared again, taking drill 14's image recipe with it, so I committed it as
`docs/operations/manifests/drill.Dockerfile`, with helm and kubectl from their release sites and
checksums verified. Then the two shapes: helm moved off `PATH`, and a pids limit equal to the pids in
use. H1 and H2 held in both. H3 was wrong in a worse direction: with helm gone, `/readyz` answered
**`200 ready`**. It only ran kubectl, and kubectl was there.

The fix classifies a spawn failure where it happens. A missing tool is `HostMisconfigured`: a `500`
that names the tool, with no `Retry-After`, because waiting won't install it. `EAGAIN` is day 33's
`HostExhausted`. `/readyz` now requires both tools. Re-run: `OrchestratorMisconfigured` fired and
`ClusterUnreachable` didn't; with helm put back, everything recovered within one scrape.

Then the documentation. I wrote the reference pages from the code, and writing them found two
defects nothing had checked. Three alerts said `severity: warn` and one said `warning`, so an
Alertmanager route on either would have missed the others. And half the alerts linked no runbook.
Both are fixed, and tests now fail the build on either. Every page in `docs/reference/` is checked
against what it describes: the settings the code reads, its routes, its series, its alert rules.
A link checker now covers every relative link in the repository, anchors included. Across about 100
Markdown files it found nothing broken except two false positives inside inline code.

The README is restructured into the usual order. CONTRIBUTING became a real contributor guide.
SECURITY.md is new, and GitHub's private vulnerability reporting is on. CHANGELOG.md is built from
the merged pull requests. The architecture page now has the failure-classification order as a
diagram, checked branch by branch against `run_bounded`.

**Got stuck on:** the line between true and tidy. The quickstart's `/metrics` excerpt is real output
from before half the series existed. I kept it, and said so, rather than invent a newer one. The
SECURITY page first claimed error details never carry a stack; that's only true for the case day 33
fixed, so it now says exactly that.

**Learned:** Writing a reference is an audit. Two of today's fixes came from documenting the alert
rules, not from a drill. A page that has to state every severity and every runbook exposes the one
that says `warn`.
