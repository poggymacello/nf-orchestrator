# 2026-09-27 — Day 32

**Focus:** Drill 12's status route had the right answer for a reason I didn't choose: Prometheus
happened to be scraping, and each scrape's 3s probe left a warm answer in the cache. Today was about
what the API tells its callers when nothing is scraping — which is exactly when they have nothing
else to go on.

**Studied:** The request path's probe order and cache again, line by line, and how the monotonic
clock behaves on Windows.

**Did:** Hypotheses first. H1: with a cold cache, a starved host and a frozen cluster, the status
route says "host overloaded" for the whole outage. H2: `/readyz`, which uses a plain 3s call, says
unreachable, so the one service gives two answers. H4: a *stopped* cluster is refused at once, and
both routes get it right.

Same starved host as drills 11 and 12, no Prometheus. The control run, with the cluster healthy,
turned up the thing I hadn't predicted: `/readyz` answered `503 kubectl get did not answer within 3s`
— a dead-cluster answer — for a cluster that was fine. The readiness check never asks for evidence,
so on a slow host it can only say "unreachable". Then the freeze. H1 held: "the delay is the
orchestrator's own host, not the cluster", 44 seconds into a real outage, in a message that also
said nothing could be known about the cluster. The two routes were each wrong in the other one's
condition. H4 held: refused within two seconds on both.

The fix treats a probe that never started as what it is — no observation of the cluster at all —
and asks once more with the 3s the scrape's probe already gets. And `/readyz` became the probe, so
it can tell "never started" from "started and got nothing back".

**Got stuck on:** a unit test that failed for a reason I didn't expect. It faked a probe that never
started, then expected the retry to start. The retry got back the same probe from the cache. The
cache check was `age <= max_age`, the retry asks for `max_age=0`, and Windows' monotonic clock ticks
every 15ms or so: an answer from the same tick has age exactly zero. It would have bitten in the
drill too. The test only caught it because a fake runs within one tick.

Re-run, same conditions: with the cluster healthy the status route now says the API server answered
in 34–146ms while the host took 2.0–2.7s; with the cluster frozen it says busy for the 30-second
recent-success window and then unreachable, and `/readyz` agrees. The price is a slower 503 on a
starved host — 7 to 10 seconds instead of 4 to 8.

**Learned:** A result that holds because of something else in the system happening to run hasn't
been tested yet — it has been observed once. Drill 12's route "worked" and I nearly wrote that down.
And "I couldn't find out" is its own answer: it must not be rounded to whichever cause the code
checks first.
