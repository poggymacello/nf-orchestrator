# 2026-09-26 — Day 31

**Focus:** Yesterday's riskiest accepted limit. A starved host "says nothing about the cluster",
and that would include a cluster that is down. If it's true, an outage can go unpaged, so I drilled
it instead of leaving it written down.

**Studied:** How `avg_over_time` treats samples that stop arriving, how promtool unit-tests alert
rules, and what klog puts on each line.

**Did:** Hypotheses first. H1: the status route says `HostOverloaded` for as long as the host is
starved, because its 0.75s probe can't start kubectl. H2, against my own finding from yesterday:
the scrape's 3s probe does start, so the scrape reports the outage once the 30-second
recent-success window runs out. H4: the host alert and the outage alert fire together, because both
things are wrong.

Drill 11's starvation, then drill 6's freeze on top once the host alert was firing. H2 held:
`nf_cluster_reachable 0` 32 seconds after the freeze, and `ClusterUnreachable` fired. H1 was wrong
in the good direction — the route said unreachable too, because it reused the scrape's probe from
the shared cache. So yesterday's finding 8 was simply wrong, and it's retired.

H4 failed twice over. The host alert **cleared** in the middle of the outage: its series only
existed when there was a round trip to subtract, and a frozen server gives none. And the throttling
alert went **pending** during a real outage. I watched the arithmetic do it: the busy series
stopped, the zeros from before the freeze aged out of the window, and six busy samples from the
first thirty seconds became 100% of what `avg_over_time` had left. It missed firing by about two
seconds.

The host fix came from kubectl's log again. I measured it before trusting it: the first line's
timestamp minus the spawn time is 0.05s idle and about 1.1s starved, whether the server answers or
not. The alert fix divides by `up` — every scrape attempted — instead of the samples that survived,
and stands down while the cluster reads unreachable.

**Got stuck on:** proving the alert fix. The second live run didn't reproduce the six busy samples,
so both rules stayed quiet on it, and a quiet alert proves nothing. That's what pushed me to
promtool. Its tests replay the drill's series: the old rule fires on them and the new one doesn't,
and drill 10's sustained and flapping throttling still reach the threshold. They now run in CI. No
alert rule in this project had ever been executed by a test before today; every check was a drill
watching Prometheus, which only ever tests the series that drill happened to produce.

Also got stuck on myself: checking that the new tests fail on `main`, I restored `orchestrator/`
with `git checkout` instead of stashing it, on a branch with no commits yet. It wiped the
uncommitted fix. I re-applied it from the edits I'd just made, got the same 202 passing, and
committed before doing anything else.

**Learned:** A range function over a series that stops is not what its name says. "The average over
two minutes" was the average of whatever was left. Series stop in exactly the incidents alerts exist
for. Separately: an accepted limit is a hypothesis nobody has tested yet. Finding 8 read as
careful humility and was simply false.
