# 2026-09-17 — Day 28

**Focus:** Yesterday's postmortem left one thing undrilled: the API server's own load shedding. The
proxy made a server slow; Kubernetes' API Priority and Fairness does something different — it answers
immediately and says no.

**Studied:** How APF assigns requests to priority levels (FlowSchemas, seats, borrowing,
`limitResponse: Reject`), which identities it exempts, and what client-go does with a 429 and a
`Retry-After` header.

**Did:** Hypotheses first. H1: client-go retries a 429, so under sustained shedding a call goes quiet
until the 3s bound kills it, and the orchestrator says "unreachable". H2: if a 429 does surface as
text, nothing classifies it, so it becomes a 502 "refusal". H3: in the scrape, throttled releases
count as `error` while reachability stays 1.

The first surprise was before the drill started: APF exempts `system:masters`, which is what kind's
admin identity belongs to, so nothing I did to flow control would have touched the orchestrator. It
ran as its own service account for the first time — read access to pods and secrets, nothing else —
which is how it should run anywhere real anyway. A FlowSchema put that account on a priority level
with three seats, no borrowing, and rejection instead of queueing. A load generator on the same
account, straight HTTPS from 40 threads so process start-up was not the limit, got real 429s from the
real API server, with `Retry-After` climbing from 1 to 32 seconds.

H1 held, and it was worse than I wrote. Status routes answered 503 "did not answer within 3s". The
first scrape set `nf_cluster_reachable 0` — the value `ClusterUnreachable` pages on — so H3 was wrong
in the dangerous direction. And `/readyz` said "reachable" in the same second. kubectl at `-v=8`
showed why: `Got a Retry-After response delay="32s"`. client-go swallows the 429 and sleeps, so the
one fact that separates the two incidents never leaves the child process.

The same readout gave the fix. `/readyz` stayed fast because Kubernetes' `probes` FlowSchema serves
health endpoints outside the throttled levels. So after a call times out, the orchestrator now asks
`/readyz` with a 0.75s bound: if it answers, the call is `ClusterBusy` — 503 with `Retry-After`,
`nf_cluster_busy 1`, `reason="busy"`, and a new `ClusterThrottlingOrchestrator` alert. If it does not
answer, nothing changes. client-go's own 429 wording is classified as busy too, for when its retries
do run out.

Re-run under the same load: status routes said *reachable and not serving this client* with
`Retry-After: 5`; a scrape that could not even list releases said reachable and busy instead of down;
Prometheus fired `ClusterThrottlingOrchestrator` after its two minutes, and `ClusterUnreachable`
never did. Then drill 7's stalled TLS server again, to make sure the probe had not turned a dead
server into a "busy" one: still unreachable, at the cost of 0.75s more per timed-out call.

**Got stuck on:** The busy signal would not clear after I stopped the load. For over two minutes it
flipped between 1 and 0 with half the releases unreported. My first thought was the API server's
`Retry-After` taking time to decay. The rejection counter said otherwise: 11 rejections a minute with
nothing but the orchestrator running. Drill 8's waves grow to eight concurrent reads, and this level
had three seats — the orchestrator was throttling itself. With the ceiling at 2: zero rejections over
two minutes, every release reported, scrapes under a second.

Also: `kubectl get --raw /metrics` answered `NotFound` twice before I remembered that Git Bash
rewrites `/metrics` into a Windows path — the same thing that mangled `/readyz` in drill 7. It is now
the first line of the new runbook. And a shell heredoc refused the postmortem because of its quoting,
so it went through the file tool.

**Learned:** A timeout is a symptom, not a diagnosis. Drill 6 bounded every call; drill 9 showed that
the bound, by killing the process, also throws away the only evidence of *why* it was slow. A second,
cheaper question asked from a different angle — is the server there at all? — gets that evidence back.

And my own fixes keep turning up as the next drill's cause. Day 25's concurrency starved a slow
cluster on day 27; day 27's waves, grown to eight, throttled the orchestrator on day 28. Neither was
wrong where it was measured. Each assumed something about the cluster's capacity that only a drill on
a different cluster could contradict.
