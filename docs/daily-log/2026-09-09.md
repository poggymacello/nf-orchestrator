# 2026-09-09 — Day 19

**Focus:** Start M6 by building the boundary the LLM will sit behind, before building
anything that calls a model.

**Studied:** How pydantic's strict mode and `extra="forbid"` behave on a dict assembled
from an untrusted source, and what OWASP's LLM guidance actually says about output
handling — the recurring advice is that model output is untrusted input to whatever
consumes it, which is a familiar shape rather than a new one.
Sources: https://genai.owasp.org/llm-top-10/,
https://docs.pydantic.dev/latest/concepts/strict_mode/

**Did myself:** Wrote `orchestrator/translate.py` and `POST /intents/translate`. The
design decision that mattered was made before any code: **translating is not deploying**.
The endpoint returns a candidate intent and stops. Putting it into the cluster is a second
call the caller makes deliberately, with the JSON in front of them. That single split
means a model cannot cause a deployment, because its output is never on the path to one,
and there is a test that asserts it by making the deploy engine's subprocess helpers raise
if translation ever reaches them.

The rest follows from treating the translator as hostile. It returns a plain dict, not an
`Intent`, so it is never trusted to have validated anything. `pick_fields` takes only
`name`, `replicas` and `environment` and drops the rest *before* validation rather than
relying on the schema to refuse them. The text is bounded at 500 characters, checked
before the translator runs, so an oversized text never reaches a third party at all.

The shipped translator is a deterministic keyword parser with no model in it —
`RuleTranslator` — which is what the guardrails are tested against and what runs in CI
with no credentials. It refuses rather than defaults: no environment in the text is a
`422`, not a quiet `dev`.

Hostile cases are unit tested against a fake translator that returns whatever it is told
to: a string instead of an object, `replicas: 500`, `environment: production`, a name of
`../../etc/passwd`, and extra `namespace` and `image` keys. 104 tests pass, ruff clean.
Wrote it up as ADR-0012.

**Got stuck on:** Less stuck than pulled toward the wrong problem. The obvious way to
start M6 is to pick a model, get a key, and make an API call, then figure out safety
afterwards. I do not have a key in this environment, which turned out to be useful — it
forced the boundary to be the deliverable instead of the demo.

The one real design argument was with myself about `pick_fields`. The schema already has
`extra="forbid"`, so a proposal carrying `image: attacker/payload:latest` would be
rejected anyway, and dropping the field first looks redundant. I kept it, because the
schema's strictness is a *setting*. Safety that holds only while a config flag stays put
is safety that ends the day someone relaxes the flag for an unrelated reason. Dropping
first means an unknown field is never even an argument.

**Learned:** The guardrails for a language model turned out to be the guardrails for any
untrusted input, and this project had already learned most of them the hard way. Do not
let a component validate its own output. Do not report a value that means "I do not know"
as one that means something specific. Do not let safety rest on a setting. The only
genuinely LLM-shaped concern was the input bound, and even that is mostly ordinary — it
matters more here because the text leaves the building.

The corollary is that a fake translator is a *better* test subject than a real model. It
can be made to return `../../etc/passwd` on demand; a real model mostly will not, which
means a live test would pass while proving much less. The thing worth asserting is not
that the model behaves — it is that it does not matter whether it does.
