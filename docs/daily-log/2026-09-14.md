# 2026-09-14 — Day 25

**Focus:** The case drill 6 could not produce — an API server that completes the TLS handshake and
then goes silent — and then the question that drill 6's fix raised without answering: its timeout
was per call, so what bounds the sum?

**Studied:** Where a scrape's time actually goes (`1 + 4 × releases` subprocesses, in series), how
`concurrent.futures.wait` with a timeout leaves running work alone while `shutdown(cancel_futures=True)`
drops queued work, and how Prometheus staleness interacts with `for:` when a series appears on some
scrapes and not others.

**Did:** Wrote both hypotheses down before running anything. H1: without the day-24 bound, kubectl
and helm would wait forever on a silent-but-connected server. H2: the per-call bound does nothing for
a scrape made of many calls, so enough healthy releases would push `/metrics` past 5s.

H1 needed no cluster: a small Python TLS server that completes the handshake, reads the request, and
never answers, plus a throwaway kubeconfig pointing at it. Both tools held the connection for the
full 120s outer timeout. With the bound, every route answered 503 in 3.03s and no processes were left
behind — but the message said `kubectl --context did not answer`, naming a flag instead of the verb.

H2 on a throwaway kind cluster, adding releases one at a time: 0.34s for one, 2.91s for eight, 4.61s
median and 5.02s worst for sixteen. Then twenty, with the repository's own Prometheus config: every
scrape `context deadline exceeded`, zero lifecycle series, and `OrchestratorScrapeFailing` firing —
yesterday's new alert, paging that the orchestrator was down while the orchestrator and all twenty
pods were fine.

Fixed with a deadline for the whole scrape (4s) and releases reconciled on a pool of eight; whatever
misses the deadline is counted instead of sinking the scrape. Twenty releases: 1.3-2.2s, all 80
series, no alerts. Forced over budget with one worker to watch that path for real: target stayed up
at 4.0s, 7 releases counted as late, and the count-based alert fired after its five minutes.

Then asked which seven. A `count_over_time` over six minutes showed `load-nf-5` to `load-nf-9` had
never had a single series — helm lists alphabetically, so the deadline lands in the same place
every scrape. A count cannot say which network functions have no alerting. Added
`nf_release_reported{release}` and made the alert per release; re-ran, and it fired naming exactly
those five. ADR-0014 records the budget, why not a cache, and why rotating the order would hide the
problem instead of fixing it. 147 tests pass.

**Got stuck on:** My own new test. After adding `nf_release_reported`, the deadline test failed
because it asserted `release="stuck-nf"` appeared nowhere in the output — and now it correctly
appears in exactly one place. The assertion had been checking a string, not the thing I meant ("no
lifecycle series"). Tightened it to `nf_deployment_state{release="stuck-nf"`.

Smaller: `bc` is not in Git Bash, so the first timing loop printed 0.0s for commands that had
clearly taken two minutes — the stall server's own log timestamps were the real measurement. And a
Prometheus query failed with a JSON error because curl treats `{}` as a glob; `curl -g`.

The README said "Three deliberate failure drills" and described the disk drill as abandoned, three
drills after both stopped being true. Day 23's doc-claims test pinned test, ADR and CI job counts
and not drills. It pins drills now, and it failed on "3 == 6" before the README was touched.

**Learned:** Drill 6's lesson was that a timeout is a budget shared with whatever downstream is also
counting. Today's is the next step: a budget has to be spent by whoever owns the total, not by each
call separately. Every individual call was fast. The failure only existed in the sum, which nothing
was responsible for.

And an alert is a diagnosis, not just a symptom. `OrchestratorScrapeFailing` was right that the
scrape failed and wrong about why, in the most expensive way — it sends someone to restart a
process that is working. Yesterday I added it to fill a gap; today it was the gap. The fix was not
to change that alert but to make the scrape stop failing for a reason it cannot describe.
