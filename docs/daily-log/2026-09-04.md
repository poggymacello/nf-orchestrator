# 2026-09-04 — Day 18

**Focus:** Finish M5 — Trivy for the chart and the dependencies — and settle the Kubernetes version
question day 16 left open.

**Studied:** What Trivy's two modes actually read: `config` parses Helm templates and evaluates them
against the KSV check bundle, `fs` needs a dependency *file* and cannot infer one from an unpinned
`pyproject.toml`. Also which Kubernetes versions `helm/kind-action`'s pinned kind can run, and how
`readOnlyRootFilesystem` interacts with nginx, which needs `/tmp` and `/var/cache/nginx` writable
and nothing else.
Sources: https://trivy.dev/latest/docs/coverage/kubernetes/,
https://github.com/nginxinc/docker-nginx-unprivileged

**Did myself:** Ran both scans before writing any CI, because a threshold picked without seeing the
findings is a guess. `trivy config` on the chart gave 2 HIGH, 4 MEDIUM, 11 LOW — root user,
writable root filesystem, no seccomp, no dropped capabilities, no resource bounds, privileged port.

Hardened the chart rather than exempting it: `nginxinc/nginx-unprivileged` on 8080, `runAsNonRoot`
with an explicit UID/GID/fsGroup, `RuntimeDefault` seccomp, `allowPrivilegeEscalation: false`, all
capabilities dropped, read-only root filesystem with `emptyDir` mounts at `/tmp` and
`/var/cache/nginx`, and CPU/memory requests and limits. That took the chart to 0 HIGH, 1 MEDIUM,
3 LOW.

Then deployed it, which matters more than the scan: 2/2 ready in ~21s, `id` reports
`uid=101(nginx)`, and `touch /etc/probe` is refused. All 6 e2e tests still pass against it.

Set the policy at fail-on-HIGH-and-CRITICAL, print everything else, with the four remaining findings
listed in ADR-0011 with reasons rather than buried in an ignore file. Pinned the e2e job to a
Kubernetes matrix of v1.34.0 and v1.35.0, so cross-version support is asserted instead of inherited
from a tool's default. Wrote ADR-0011 and the M5 build log.

**Got stuck on:** Trivy's dependency scan reported this against the whole repository:

```
│ Target │ Type │ Vulnerabilities │
│   -    │  -   │        -        │
Legend: '-': Not scanned
```

Every column a dash. Nothing was scanned, because `pyproject.toml` lists three unpinned
dependencies and there is no lockfile, so Trivy had no file it could read. It would have reported
clean forever. That is yesterday's lesson arriving from a different direction — a gate that reports
success while doing nothing — one day after I wrote an ADR about exactly that failure mode. Fixed by
having CI freeze what it installs and scan that: `-` became `requirements.txt / pip / 0` across 35
packages. Then checked it can fail, against `urllib3==1.24.1` and friends: 8 vulnerabilities,
exit 1.

Two smaller ones. I reported `make trivy exit=0` to myself before noticing `make` is not installed
on this machine at all — the exit code I read was the `grep` at the end of the pipe. `mingw32-make`
exists, and running the target properly then failed for a real reason: Git Bash rewrites `/repo`
into `C:/Program Files/Git/repo` before docker sees it. `MSYS_NO_PATHCONV=1` in the recipe, ignored
everywhere else, fixes it.

**Learned:** Hardening moved a finding instead of removing it. Clearing 2 HIGH and 3 MEDIUM by
switching to the unprivileged image introduced a new MEDIUM — the image now comes from a different
Docker Hub path, and Trivy checks images against trusted registries. The count went down and the
list changed shape, which is a more honest way to read a security scan than a single number.

The other thing is about the four gates as a set. Three of them were wrong on the first attempt, and
every one passed its happy path while broken: Gitleaks blind to the fixture I picked, my own scanner
leaking through the paths, Trivy scanning nothing at all. A scanner that finds no problems and a
scanner that is switched off produce identical output, and the only way to tell them apart is to
make each one fail on purpose. I have now done that three times in two days and been surprised three
times.
