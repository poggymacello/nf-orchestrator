# 2026-09-13 — Day 24

Second session the same day.

**Focus:** Drill the one risk an ADR had written down and nobody had tested — ADR-0007's
"nothing times these subprocesses out yet".

**Studied:** What `docker pause` does to a network path (the proxy still accepts TCP; nothing
behind it answers), Go's `net/http` transport defaults, and how Prometheus treats an unset
`scrape_timeout` — it is clamped to the scrape interval.

**Did myself:** Wrote the hypothesis down first: with no timeout on any helm or kubectl
call, a frozen control plane would hang the status endpoint and the scrape indefinitely.
Then froze a throwaway cluster's node with `docker pause`.

The hypothesis was wrong. Everything answered in ten seconds with correct 503s. The error
explained it — `net/http: TLS handshake timeout` — which is Go's default inside kubectl and
helm. This project had no bound of its own; it was protected because this particular failure
stalled before the TLS handshake. A server that completes the handshake and then stalls would
not have been caught.

The real finding came from following that ten seconds to the thing measuring it. The repo's
Prometheus config scrapes every 5s with the timeout clamped to 5s. Run for real against the
frozen cluster: target `down`, `context deadline exceeded`, and **`nf_cluster_reachable` had
no series**. The orchestrator was computing the right value and Prometheus abandoned the
scrape before receiving it, so `ClusterUnreachable` — `nf_cluster_reachable == 0` — could not
fire during the outage it exists for.

Fixed: every call goes through `run_bounded` with a 3s read bound (inside the scrape timeout,
pinned by a test) and a 60s write bound, and a timeout becomes `ClusterUnreachable`.
`scrape_timeout` is now stated. Added `OrchestratorScrapeFailing` on `up == 0`, because every
other rule reads a metric that only exists if the scrape succeeds. Re-ran: routes in 3.0s,
scrape up, `ClusterUnreachable` firing. Then stopped the orchestrator to watch the new rule
fire rather than assume it would — it did, and `ClusterUnreachable` went *inactive* as its
series went stale. Without the new rule, the outage alert would have cleared at the moment
things got worse. 140 tests pass.

**Got stuck on:** My own fix broke Prometheus. After the timeout change, the re-run showed the
orchestrator fixed and Prometheus returning nothing; it had exited on `invalid leading UTF-8
octet`. I had added the `scrape_timeout` line with Python's `write_text()`, which on Windows
writes cp1252, and the em dash in my comment became byte `0x97`.

The part worth keeping: I had verified that edit. `yaml.safe_load(open(...))` said the file
was fine. It opened the file with the same default encoding the writer used, decoded the same
byte the same way, and agreed with it. A check that shares the writer's assumptions cannot
find the writer's bug. The real test was Prometheus, a reader that did not share them.

Added a strict UTF-8 check over the configs and docs, and made it fail on a cp1252 probe file
before trusting that it passes. Also: yesterday's doc-claims test failed on its first real use
today — four new tests, README still saying 135 — which is the whole reason it exists.

**Learned:** Two drills in a row now, the interesting failure was not at the component I was
testing but at whatever was *observing* it. Drill 5's bug appeared in the recovery. Drill 6's
appeared one layer out, in Prometheus's clock, where a latency that was harmless on its own
became an outage alert with no data. A timeout is not a property of one call; it is a budget
shared with everything downstream that is also counting, and ten seconds is fine until
something else only waits five.

And the encoding bug is the cleanest example yet of a pattern this project keeps finding:
verification that passes because it agrees with the thing it is verifying. Gitleaks and its
allowlisted fixture on day 17, the self-referential test term on day 17, and now a YAML check
decoding with the writer's encoding. The fix every time is a check that does not share the
assumption.
