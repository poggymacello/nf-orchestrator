# 2026-10-16 — Day 35

**Focus:** The gap drill 15's postmortem admitted: a tool that is present but the wrong version.
The orchestrator's promise never to overwrite another manager's field rests entirely on Helm 4, and
until today nothing checked which helm was installed.

**Studied:** How Helm 3 and Helm 4 differ: client-side three-way merge against server-side apply, and
what `--set-json` accepts in each.

**Did:** Hypotheses first. H1: under Helm 3, drill 3's drift scenario succeeds silently. The
resubmit overwrites `kubectl scale`, the API answers 201, and ADR-0008 is broken without anyone
noticing. H2: `/readyz` says ready and no metric differs. H3, to measure rather than assume: the
orchestrator's helm JSON parses the same under both.

Two images from the committed drill Dockerfile, identical except for the helm version: 4.2.2 and
3.19.0, both checksum-verified. Helm 4 behaved as designed, with the conflict answered `409`. Helm 3
never got that far. H3 failed first: Helm 3's `--set-json` takes `key=value` pairs, not the whole
object the orchestrator passes, so every deploy failed with `failed parsing --set-json data`. That
was answered `502`, "the cluster refused", for a request the cluster never saw. H2 held: `/readyz`
200, `nf_orchestrator_misconfigured` 0, and reads working fine.

I didn't want to leave H1 as a guess in the ADR, so I measured it with the Helm 3 CLI directly, using
`--set`, which Helm 3 accepts. After `kubectl scale` to 1, `helm upgrade` said `STATUS: deployed` and
quietly put the Deployment back to 2. The parse error had been the lucky failure. The orchestrator's
argument format happened to stop Helm 3 before it could overwrite anything.

The fix makes that refusal deliberate. Helm's major version is checked, cached for a minute, before
every write, in `/readyz` and in every scrape. A wrong major is a `500` naming the version found and
the one required, and pages through the same alert as a missing tool. The parse error is classified
as the host's, for a helm swapped while the cached answer is still valid. Re-run: under Helm 3,
`/readyz` and every write are `500` with the version named and the gauge is 1. Under Helm 4, the
conflict is still `409`.

**Got stuck on:** where a version check belongs. Only at start-up misses a binary swapped under a
running process. On every call adds a process to every request. A one-minute cache, plus the
classifier for the gap, covers both at the cost of one `helm version` a minute.

**Learned:** A safety property that rests on a dependency's version is only as strong as the
check on that version, and a pin in CI and a line in the README are not runtime checks. Also: the
failure I predicted (H1) was real, and was hidden behind a different, louder one. Fixing only the
loud failure — say, by changing the argument format — would have exposed the quiet one.
