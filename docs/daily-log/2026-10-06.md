# 2026-10-06 — Day 33 (finished 2026-10-07)

**Focus:** The last host failure I hadn't touched: a host that cannot start processes at all. Every
cluster call is a child process and every route runs on a thread. In a container that's a pids
limit; on a laptop it's memory running out. Since day 12, a failed spawn has been grouped with an
unreachable cluster.

**Studied:** Windows Job Objects and their process limits, how Linux's `pids.max` counts threads,
and what the Go runtime does when it can't get one.

**Did:** Hypotheses first. H1: a failed spawn makes the scrape report the cluster unreachable. H2:
the status route returns a bare 500. H3: the host alert stays silent, because a spawn that fails is
fast. H5: failures follow concurrency, not releases.

I started on Windows with a Job Object limiting the orchestrator's process tree, and checked it on a
throwaway process before trusting it. It allowed four of four children at a limit of **one**. The
venv's launcher runs Python inside its own job with silent breakaway, so every child escapes. I
dropped it, and since it was now a Linux drill I added H6 before running anything: `pids.max` counts
threads, so Python's own thread pools will fail too. Then I put the orchestrator in a container on
the kind network, with helm from its release site and kubectl copied out of the kind node.

The baseline taught me something first: 7 pids at rest, 57 at a scrape's peak. helm and kubectl are
Go, and each starts about ten threads.

At a limit of 30, H5 held: eight of ten releases were `reason="error"` on every scrape, while a
single status call worked. Nothing recorded why, so I reproduced it by hand inside the container,
and Python couldn't even start eight threads for the test. With three, helm said it plainly:
`runtime: failed to create new OS thread ... fatal error: newosproc`. The fork had worked — one pid
— and the crash came afterwards. So H1's mechanism was wrong, but its outcome held at a limit of 15:
the crash text was a plain `DeployError`, the listing failing made the scrape say
`nf_cluster_reachable 0`, and the API answered 502, "the cluster refused", with 18,933 bytes of Go
stack. Five of six concurrent requests got bare 500s from Starlette's thread pool, before any of my
code ran.

The fix names it: `HostExhausted`, a host-overloaded 503 that keeps the runtime's first two lines.
In the scrape it counts as `reason="host"` with no claim about the cluster, and every place that
starts a thread records the failure instead of dying of it. A gauge reports it, and the host alert
gained a second half, promtool-tested against the drill's series.

**Got stuck on:** two shell commands that never ran — one a quoting failure, one stopped by a safety
check that couldn't read a `bash -c` script next to `docker rm`. I moved the edits into script files,
which I should have done from the start. And overnight Docker Desktop restarted and took the drill
container with it (exit 255). The kind nodes came back on their restart policy; the container didn't
have one. That cost a restart, not a finding.

Verified the next day with Prometheus running. Before: `ClusterUnreachable` firing for a healthy
cluster, the host alert inactive. After: the host alert firing, `ClusterUnreachable` quiet, every
response a 503 that names the host, `reason="host"` instead of `"error"`, and recovery at the next
scrape once the limit was lifted.

**Learned:** "Could not run" and "ran and was told no" were sharing one exception class, so the
default classification for anything unrecognised was "the cluster refused". That's the most
damaging default available: it points away from the machine actually at fault. And a test harness
I haven't seen bind isn't a test harness. The Job Object would have produced a clean-looking pass.
