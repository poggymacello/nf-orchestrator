# 2026-08-20 — Day 11

**Focus:** Run the first two failure drills against the real cluster and write the postmortems and
runbooks from what actually happened. First session back after a month away from the project.

**Studied:** Kubernetes pod phase versus container status — that `phase: Running` is a statement
about the pod being scheduled with at least one container started, not about any container being
usable, and that `containerStatuses[*].ready` and pod conditions are the readiness signal. Also
kind's kubelet defaults, which turn out to disable disk eviction entirely.
Sources: https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/,
https://kubernetes.io/docs/concepts/scheduling-eviction/node-pressure-eviction/

**Did myself:** Drill 1, pods killed mid-deploy. Deployed a 3-replica intent and deleted all three
pods three polls in, with a sub-second poller already running — the Day 9 lesson about needing an
observer in place before the event. The workload recovered in about two seconds. The reporting did
not hold up. At 20:48:15 the reconciler said `INSTANTIATED` with six pods live for a three-replica
intent. Chasing that, I scaled the Deployment to 1 outside Helm: `helm get values` still said
`replicaCount: 3`, the cluster had 1, and the endpoint still said `INSTANTIATED`. The reconciler
has no idea how many replicas the intent asked for — `reconcile()` takes a name and nothing else.

Drill 2, control plane unreachable. Stopped the kind node with a release running. The deploy path
was fine: 502 in under a second with the real Helm error passed through, and
`deployments_total{result="failed"}` incremented, so the M4 counter got exercised against a failure
it had never seen. The read path returned **HTTP 200 with `NOT_INSTANTIATED`** for an NF that was
running the whole time — byte-identical to the response after a genuine teardown. `docker start`
brought it back in ~5s with the release intact.

Wrote both postmortems, two runbooks, and `docs/operations/` from the captured output. Every
command in the runbooks is one I ran during a drill. Cluster left clean: release uninstalled, kind
still up.

**Got stuck on:** Drill 2 was supposed to be "disk full". Setting it up, I found kind ships
`evictionHard` with `nodefs.available: 0%` and `imagefs.available: 0%` — disk eviction is switched
off — and the node's filesystem is the host's, showing 848G available. Producing `DiskPressure`
would have meant writing ~760 GB to my own disk to cross a threshold that does not exist. Abandoned
it and substituted the control-plane drill, which is recoverable in seconds and asks the same
question. Also spent a while on a wrong assumption: I expected deleted pods to report `Running` with
a `deletionTimestamp`. They report `Succeeded` — nginx exits 0 on SIGTERM — which the reconciler has
no branch for at all.

**Learned:** Both drills found the same defect wearing different clothes. The reconciler answers
"is everything I found healthy?" when the question is "is what was asked for actually running?" It
never reads desired replicas, it detects failure by matching three hardcoded waiting-reason
strings, and it collapses "cannot reach the cluster" into the same `None` it uses for "no such
release". That last one is the one that would hurt: during a control-plane outage every deployment
in an estate would appear to tear itself down, at HTTP 200, and anything automated watching for
`NOT_INSTANTIATED` would act on it. A monitoring system that is down is a Sev-2. One that
confidently reports the wrong state is a Sev-1, which is why both drills are filed that way.

Second thing: a state derived per request is an instant, not a state. Drill 1 flapped
`INSTANTIATING → INSTANTIATED → INSTANTIATING → INSTANTIATED` in three seconds during a completely
normal pod replacement. Alerting on one read of that endpoint would page on nothing.
