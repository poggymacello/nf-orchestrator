# 2026-07-23 — Day 9

**Focus:** Build the M3 status reconciler and teardown, watch the real lifecycle-state sequence it
derives from cluster signals, and reconcile the Day-5 lifecycle doc against what I observed.

**Studied:** How ETSI NFV SOL003 splits instantiation state from operation state, and how a
reconciler projects raw Kubernetes/Helm signals onto a small enum.
Sources: https://www.etsi.org/deliver/etsi_gs/NFV-SOL/001_099/003/03.05.01_60/gs_NFV-SOL003v030501p.pdf,
https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/

**Did myself:** M3 did not exist at the start of the day. Wrote `orchestrator/reconciler.py`: a
pure `derive_state(helm_status, pod_phases)` that returns one of the four states, plus readers
using `helm status --output json` and `kubectl get pods -o json`, and two routes, `GET
/deployments/{name}` and `DELETE /deployments/{name}`. State is derived on read, not stored.

Observed all three real sequences. Success, polled sub-second while pods came up: `NOT_INSTANTIATED`
(no release) then at 08:11:43 `INSTANTIATING` with pods `Pending/ContainerCreating`, then at
08:11:44 `INSTANTIATED` with both pods `Running`. Failure, by upgrading to a nonexistent image tag:
`FAILED` at 08:14:16 from a pod `ErrImagePull` settling to `ImagePullBackOff`, while `helm status`
stayed `deployed` the whole time, so the state came from the pod reason, not the release. Teardown,
`DELETE` ran `helm uninstall`, `helm list` then showed the release gone and no pods remained, and
the next read reported `NOT_INSTANTIATED`. Thirty tests pass and `ruff check .` is clean; the
derivation is unit tested with mocked signals since CI has no cluster.

**Got stuck on:** The success transition was invisible on the first attempt. Polling once per
second after the deploy returned only ever caught `INSTANTIATED`, because the nginx image was
cached and `ContainerCreating → Running` took under a second, so the whole `INSTANTIATING` window
fell between two polls. The derivation was fine; the observation was too slow. Fixed by tearing
down and starting a sub-second poller before submitting, which caught the `INSTANTIATING` frame.

**Learned:** A `deployed` Helm release is not a healthy workload, and a reconciler that trusts
release status would report success over a pod stuck in `ImagePullBackOff`. Reading pod
waiting-reasons is what makes `FAILED` honest. Also that `FAILED` on a rolling upgrade means the
current rollout is failing, not that the service is down, since the old pods keep serving.
