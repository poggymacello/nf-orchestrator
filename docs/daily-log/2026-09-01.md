# 2026-09-01 — Day 15

**Focus:** Close the last unfixed drill defect — a failed Helm *operation* being reported as a failed
*deployment* — and decide whether the M3 decision to collapse ETSI's two lifecycle attributes into
one enum still pays.

**Studied:** ETSI SOL003's split between `instantiationState` and `LcmOperationStateType` more
carefully than when I first wrote the lifecycle doc on Day 5, and Helm's full set of revision
statuses — `deployed`, `failed`, `superseded`, `uninstalling`, `pending-install`, `pending-upgrade`,
`pending-rollback` — and which of them can appear as the newest revision.
Sources: https://www.etsi.org/deliver/etsi_gs/NFV-SOL/001_099/003/03.05.01_60/gs_NFV-SOL003v030501p.pdf,
https://helm.sh/docs/helm/helm_history/

**Did myself:** Split the two axes. `derive_state` no longer returns `FAILED` because a Helm
operation failed — `FAILED` comes from workload signals only, as ADR-0006 defined them. The
operation is reported beside the state as `last_operation`, carrying the revision, an
`OperationState` (`PROCESSING` / `COMPLETED` / `FAILED` / `UNKNOWN`, a subset of SOL003's type), and
Helm's own error text as the description. It reads from `helm history`, which the reconciler already
called for `desired_replicas`, so it costs no extra subprocess.

`UNKNOWN` is there because of drill 1: a Helm status nobody anticipated must not land in a bucket
that means something specific. That is the exact mistake `Succeeded` made when it fell through to
`INSTANTIATING`.

Also added `nf_last_operation_state{release,state}` and an `NFLastOperationFailed` rule at
`for: 5m`, `severity: warn` — softer and slower than the NF alerts, because an unresolved failed
operation is something to go and tidy up, not an outage.

Verified on the cluster. Drill 3's case rebuilt: healthy → drift → conflicting resubmit now reads
`INSTANTIATING` with `ready_replicas: 1` and `last_operation.state: FAILED`, where on day 14 the
same situation read `FAILED`. A repair takes it back to `INSTANTIATED` / `COMPLETED`. 74 tests,
`ruff check .` clean, cluster left empty.

**Got stuck on:** I had the wrong design for about twenty minutes and only caught it by trying it
against a real release. The strict SOL003 reading says instantiation either completed or it did not,
so a release whose first install failed should be `NOT_INSTANTIATED` with the operation `FAILED`. I
had already written `ever_deployed` into the derivation to do exactly that.

Then I looked at what such a release actually is: a Helm release that exists, with a pod sitting in
`ImagePullBackOff`. Reporting `NOT_INSTANTIATED` would put it in the same bucket as a name that was
never deployed and a release that was torn down — and `NOT_INSTANTIATED` is what `DELETE` returns and
what the teardown path checks for. I would have fixed drill 3's collapse by building drill 2's
collapse somewhere new.

So `NOT_INSTANTIATED` keeps meaning exactly one thing, no release exists, and a failed install stays
`FAILED`. `ever_deployed` survived, but only for the narrow case where nothing ever deployed *and*
the operation failed — otherwise that release would report `INSTANTIATING` forever, since with no
pods and no desired count nothing else fires.

**Learned:** Every M4 drill found the same shape of bug: two things that are usually equal, collapsed
into one value, diverging only when something goes wrong. Pod phase versus container readiness.
Release-absent versus cluster-unreachable. Intent submitted versus intent applied. Operation failed
versus network function failed. Four instances, three drills, and in each case the collapse was
invisible in every test I had written because the two halves agree right up until an incident.

The thing I want to keep is narrower than "avoid collapsing concepts", because collapsing is often
correct — M3 collapsed these two on purpose and got a simpler reconciler for three milestones out
of it. What made it survivable was that ADR-0005 and the lifecycle doc *wrote the collapse down*
as a known simplification. Drill 3 did not discover an unknown; it turned a documented trade-off
into a priced one. A collapse you have recorded is a decision, and a collapse you have forgotten is
a bug waiting for an incident.
