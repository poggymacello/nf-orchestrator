# 2026-09-02 — Day 16

**Focus:** Start M5 by getting kind into CI, so the M4 failure drills stop being something that only
works on this laptop.

**Studied:** GitHub Actions job-level concurrency and `cancel-in-progress`, why third-party actions
are pinned to a commit SHA rather than a tag (a tag can be moved onto different code, a commit
cannot), and what `helm/kind-action` actually installs — it pins its own kind and kubectl versions,
which turned out to matter.
Sources: https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions,
https://github.com/helm/kind-action

**Did myself:** Wrote `tests/e2e/test_lifecycle_e2e.py`, six tests that drive the real API against a
real cluster: nothing deployed reads `NOT_INSTANTIATED`; an intent reaches `INSTANTIATED` with
2 of 2 ready and `last_operation` `COMPLETED`; drift applied with `kubectl scale` shows as a
shortfall, a resubmit is refused with `409`, the failed operation does not make the NF read `FAILED`,
and repair takes the field back; a bad image tag reaches `FAILED`; teardown is idempotent; `/readyz`
answers. That is the ground drills 1 and 3 covered by hand, plus the day-15 split, now executable.

They skip themselves unless `NF_E2E=1`, so `pytest` and the `lint-test` job stay a no-cluster run —
74 passed, 6 skipped. Ran them locally against the kind cluster first: 6 passed in 31s. Added
`make e2e` running the same command CI runs.

Then the workflow. A second job, `e2e`, that installs Helm 4.2.2 and creates the kind cluster from
the repo's own `kind-config.yaml`. Helm 4 specifically: the conflict behaviour these tests assert
does not exist in Helm 3, which merges client-side and would silently win, so a job on Helm 3 would
pass for the wrong reason. Both third-party actions are pinned to commit SHAs. Added
`permissions: contents: read`, job timeouts, a concurrency group that cancels superseded runs, and a
diagnostics step that dumps pods and events only `if: failure()`.

CI now also triggers on every branch push, not just `main` and pull requests. That was not a
stylistic choice: this project works on long-lived day branches, there are six of them unmerged, and
none had ever been through CI at all.

Pushed and watched a real run rather than assuming: `lint-test` green in 17s, `e2e` green in 88s,
6 passed in 22.15s inside the job.

**Got stuck on:** Docker Desktop was not running — the machine had been restarted overnight — so the
first local e2e run failed all six tests with `/readyz` returning 503. That is the day-12 work
behaving exactly as designed: the readiness endpoint said the cluster was unreachable instead of the
tests reporting nonsense about deployments. It cost a minute to diagnose because the failure named
its own cause.

The more interesting one came out of the CI log. `helm/kind-action` pins its own tooling, so the job
ran **Kubernetes v1.35.0 and kind v0.31.0**, while every drill in M4 was run against v1.36.1 locally:

```
v4.2.2+gb05881c
Client Version: v1.35.0
nf-orchestrator-control-plane   Ready   control-plane   22s   v1.35.0
```

I had pinned Helm carefully and let Kubernetes float without noticing. It passing on 1.35 is a
better result than passing on 1.36 would have been — the drill behaviours are not specific to the
version I happened to have — but that was luck, not design. Pinning the Kubernetes version, or
deliberately running a matrix, is a real decision I have not made yet.

**Learned:** The e2e job is worth more than the assertions in it. Every M4 drill finding came from
watching the real system do something surprising, and each fix was verified once, by hand, on one
machine, on one Kubernetes version. Those verifications had no way of failing again if a later
change broke them. Now they do, on hardware I do not own, on a version I did not choose.

What the job does *not* cover is worth writing down too. Drill 2 — control plane unreachable — is not
in it. Stopping the kind node mid-job is possible but would make a failure hard to tell apart from
a flaky runner, and the unreachable paths are already unit tested against the exact strings the
drill produced. The e2e job covers the drills whose evidence is a state transition, not the ones
whose evidence is an outage.
