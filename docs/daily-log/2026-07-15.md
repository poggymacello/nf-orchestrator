# 2026-07-15 — Day 3

**Focus:** Exercise intent validation and capture real rejection errors.

**Studied:** Pydantic v2 validation and error handling, JSON Schema basics.
Sources: https://docs.pydantic.dev/latest/concepts/models/,
https://docs.pydantic.dev/latest/errors/validation_errors/, https://json-schema.org/understanding-json-schema

**Did myself:** No intent-submit endpoint exists yet (M1), so wrote
`scripts/intent_validate.py` — a minimal `Intent` pydantic model (`name`, `replicas`,
`environment`) — and ran one valid payload plus three invalid ones (missing required field, wrong
type, bad enum value) through it. Captured the real `ValidationError` output for each: `missing`,
`int_parsing`, and `literal_error`, each with `loc`/`msg`/`input`.

**Got stuck on:** Assumed a wrong-type value would always be rejected, but `"replicas": "3"` gets
silently accepted and coerced to `int(3)`, while `"replicas": "two"` gets rejected. Pydantic v2's
default mode coerces any string parseable as an int rather than requiring the type to already
match. Confirmed by running both through `Intent.model_validate` directly.

**Learned:** Pydantic collects every field violation into one error list per request instead of
failing on the first one, and each error carries a distinct `type` (`missing`, `int_parsing`,
`literal_error`) that a caller can branch on instead of parsing the message string.
