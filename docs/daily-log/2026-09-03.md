# 2026-09-03 — Day 17

**Focus:** Build the two CI gates `CONTRIBUTING.md` has listed as `(planned, M5)` since M1 —
Gitleaks for credentials, and a grep for private terms — and make sure neither of them leaks.

**Studied:** What Gitleaks actually does and does not flag, including its allowlisting of published
example credentials; and how GitHub Actions masks secrets in logs — it masks the secret's *value*,
which for a newline-separated list is the whole list, not the individual lines inside it. That
detail decided the design of the term scanner.
Sources: https://github.com/gitleaks/gitleaks,
https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions

**Did myself:** Two jobs. `secret-scan` runs the Gitleaks image, pinned by digest, over a
`fetch-depth: 0` checkout — history rather than the diff, because a key committed in July and
deleted in August is still in the pack file. It found nothing across 52 commits.

`banned-terms` runs `scripts/scan_banned_terms.py`, which reads the term list from `BANNED_TERMS`
rather than from the repository. Committing the list of things that must never be committed would
defeat the whole exercise. A match is reported as a location plus an index into the list — never the
term — because a public CI log is precisely where a private term must not appear, and GitHub will
not mask an individual line of a multi-line secret. The gate fails closed: unset exits 2 with an
explanation, not 0.

Wrote it up as ADR-0010, added `make scan`, and updated CONTRIBUTING, which can now say that two of
the checklist's items are mechanical instead of remembered.

**Got stuck on:** Both gates lied to me on the first attempt, in opposite directions.

Gitleaks first. I made a file containing an AWS key id and secret, ran the scanner at it, and got
`no leaks found`, exit 0. Nothing was wrong with the scanner: I had used `AKIAIOSFODNN7EXAMPLE` and
`wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY`, which are the canonical examples from AWS's own
documentation, and Gitleaks allowlists them deliberately. Re-tested with a `ghp_`-shaped token, an
RSA private key block, and a plausible AWS pair: all three detected, exit 1. Had I only run the
positive test — scan the clean repo, see it pass — I would have shipped a gate that catches nothing
and believed it worked, because the fixture I chose was the one value in the world designed not to
trigger it.

Then my own scanner. Running it against a term that appears in this repo, the output was correctly
redacted on every line — and leaked the term **49 times anyway**, through the file paths:
`docs/build-log/m3-reconciler.md:1: matches term #1 (redacted)`. A file *named* after a private term
publishes it through the location alone. Added path redaction, so that reads
`docs/build-log/m3-***.md:1`, and re-ran the same check: 0 lines containing the term, still exit 1,
still actionable. There is now a test named after the bug.

**Learned:** A security gate is the one kind of code where the passing test proves almost nothing. A
scanner that finds no secrets in a clean repository and a scanner that is switched off produce
identical output. Both of today's gates behaved perfectly against the happy path and were broken —
one blind to the fixture I picked, one leaking through a channel I had not thought of — and the only
thing that surfaced either was deliberately trying to make them fail.

That is the same lesson the M4 drills kept teaching, one layer up. There, the system reported wrong
state and only a deliberate failure exposed it. Here, the thing that reports on the system was
wrong, and only a deliberate failure exposed that. Verification has to reach the tools, not stop at
the system they watch.

Second, smaller: the redaction bug came from thinking of "the output" as the line content and
forgetting the metadata around it. The leak was not in what I printed about the file, it was in
naming the file.
