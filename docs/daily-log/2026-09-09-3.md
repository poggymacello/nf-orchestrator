# 2026-09-09 — Day 21

Third session the same day. M6's remaining work needs an API key this machine does not
have, so this is M7's publish pass instead.

**Focus:** Read the whole documentation set as a stranger would, and fix what it claims
that is no longer true.

**Studied:** Nothing new. This was an audit, and the interesting part was that the audit
had to be mechanical — I have written most of these documents and am the worst available
judge of whether they still say true things.

**Did myself:** Grepped for the shapes staleness takes — `(planned`, `not yet`, `does not
exist yet`, `in progress` — and separately for every number the docs assert, then compared
each against the repository. That found more than reading would have:

- `docs/design/00-overview.md` still said "M5 is in progress" and "The LLM intent layer is
  M6 and does not exist". Both stopped being true on days 18 and 19.
- The same file said "three deliberate failure drills". There are four.
- `README.md` claimed **74 unit tests** (122), **8 ADRs** (12), and described CI as two
  jobs (five).
- `docs/README.md` opened with "Early."
- The Makefile's `demo:` target still echoed `"wired up in M2 once the deploy engine
  exists"`. M2 shipped on day 8, eleven days before I first read that line and did not
  notice it.

Fixed all of them, replaced the `demo:` placeholder with something that actually tells you
what to run, and added a `docs/build-log/README.md` index — the directory was linked from
the docs table and had no front page, so it opened as a bare file listing.

Also added a note to the README explaining why its own CI badge is red: `banned-terms`
fails closed without its secret, which is the design, but a red badge with no explanation
just reads as a broken project.

**Got stuck on:** The milestone map had promised two M0 documents since day 1 —
`build-log/m0` and `ADR-0002 (FastAPI)` — and neither existed. Eight weeks of a row saying
"docs: in progress".

The build log was straightforward and worth writing: days 1 to 6 of the daily log are full
of specific, dated evidence, so I assembled it from those entries and said at the top that
is what it is. It turned out to be the most interesting build log in the set, because M0 is
where two findings that shaped everything later were first seen — `helm upgrade` reporting
success over a pod in `ImagePullBackOff` (day 4), and `helm status` staying `deployed`
through a failed rollout (day 5). Those became ADR-0005, and M4 spent three drills finding
the places the reconciler had not taken them seriously enough.

ADR-0002 I did not write, after starting to. I could have assembled a plausible rationale
for FastAPI from the code — pydantic models are the intent contract, `/intents/schema`
serves `Intent.model_json_schema()`, ASGI. But the daily logs contain no evidence the
choice was ever deliberated: day 2 *runs* FastAPI, it does not choose it. Writing a
confident retrospective ADR would have been inventing a decision record, and
[ADR-0001](../design/adr/0001-record-architecture-decisions.md) — the very first document
in this repository — exists to say that rationale reconstructed after the fact is lossy.
Manufacturing one would have contradicted the reason the ADR habit exists. The map now
records the gap instead of pointing at a file that was never going to appear.

**Learned:** The staleness was concentrated in exactly the documents I touch least. Every
ADR was still accurate, because an ADR is a dated record of one decision and does not go
out of date — it gets superseded, which is a different thing, and ADR-0005, 0006 and 0009
all say so on their own front matter. What rotted was every document that describes *the
current state*: the overview, the README, the docs index, the milestone map. Those are also
the four a stranger reads first.

So "documents go stale" is too vague to act on. Status prose goes stale; decision records
do not. The fix is not to write fewer status documents but to know that they are the ones
carrying a maintenance cost, and to check them mechanically rather than by re-reading, since
the author is the person least able to see a claim that used to be true.
