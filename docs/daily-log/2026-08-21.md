# 2026-08-21 — Day 12

**Focus:** Fix what the two failure drills found, in code with tests, and re-run both drills against
the fixed build instead of trusting that the fixes work.

**Studied:** How Kubernetes actually reports readiness — `containerStatuses[*].ready` and pod
conditions versus `status.phase` — and what a `deletionTimestamp` means for a pod that still appears
in `kubectl get`. Also Helm's `get values --all`, which returns the coalesced values including chart
defaults, making it a durable record of what an intent asked for without adding a database.
Sources: https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/,
https://helm.sh/docs/helm/helm_get_values/

**Did myself:** Three fixes, all from the drill findings.

`derive_state` now takes the desired replica count and only reports `INSTANTIATED` when the pod
count matches it and every pod is ready. `desired_replicas()` reads it from `helm get values --all`
— deliberately not from `Deployment.spec.replicas`, because that is whatever last wrote to the
Deployment, and under it drill 1's `kubectl scale` drift would be undetectable by construction.
`pod_states()` skips pods with a `deletionTimestamp`, which is what stopped the pod count doubling
mid-replacement, and returns a `ready` flag per pod. A non-terminating pod in `Succeeded` or
`Failed` is now `FAILED` instead of falling through to `INSTANTIATING`.

`ClusterUnreachable` is a new `DeployError` subclass, raised by `classify_error()` when helm's or
kubectl's output matches a known unreachable wording. `helm_release_status()` returns `None` only
for `release: not found` now; unreachable propagates, and so does any error it does not recognise.
Every route maps unreachable to `503` and other cluster refusals to `502`. Added `/readyz` doing
`kubectl get --raw=/readyz`, and pinned `/healthz` as liveness-only with a test that asserts it
stays green while the cluster is down, so that stays a decision rather than an accident.

Then re-ran both drills. The shortfall case now reads `INSTANTIATING desired=2 ready=1`. Killing all
three pods of a 3-replica intent never pushed the counted pods above three, and the state moved on
readiness dropping to 0, not on pod phases. With the node stopped, `GET`, `POST` and `DELETE` all
returned 503 with the real error, `/healthz` stayed 200 and `/readyz` returned 503. Checked the
`FAILED` path had not regressed by upgrading to a nonexistent tag — still `FAILED` on
`ErrImagePull`. 51 tests pass, `ruff check .` clean, cluster left empty.

Wrote ADR-0006 for the revised derivation, marked ADR-0005 superseded in part, updated the lifecycle
state table, closed 6 of the 8 action items across the two postmortems, and rewrote the parts of both
runbooks that warned about behaviour that no longer exists.

**Got stuck on:** The `DELETE` path during an outage, which I had not exercised in drill 2 at all.
Before the fix it went `helm_release_status` → `None` → "no release here" → `{"uninstalled": false}`
with HTTP 200 — reporting a successful idempotent teardown of a release that was still running. The
original drill missed it because I only tested the read and deploy paths. One collapsed error case
had produced three wrong answers, not one, and I only found the third by fixing the first two.

Also could not reproduce the `CreateContainerConfigError` window on the 08-21 replay — kubelet
synced faster this time — so that finding is closed on the strength of a unit test rather than a
second live observation. Recorded it that way rather than implying I saw it again.

**Learned:** Both drill findings were the same mistake in two places: answering a question that was
easier than the one being asked. "Are the pods I found healthy?" instead of "is what was asked for
running?", and "did the command fail?" instead of "did it fail because the thing is absent, or
because I could not look?". The fix in both cases was to make the function require the information
it was quietly doing without — a `desired` argument it cannot default, and an exception type that
cannot be flattened into a sentinel.

The other thing worth keeping: putting `desired_replicas` and `ready_replicas` in the response body
matters as much as the logic change. Drill 1's wrong answer would have been obvious to anyone
reading the payload. A derived state should carry the numbers it was derived from.
