# 2026-09-16 — Day 27

**Focus:** The case ADR-0014 wrote down as a cost and never ran: an API server that still answers,
slowly, while my own fix sends eight readers at it.

**Studied:** What makes an overloaded server different from a slow one — latency alone versus
latency plus a queue — and how a queue interacts with work that comes in pairs.

**Did:** Hypotheses first. H1: with a constant added latency the scrape lands around 2.3s at 30
releases and loses nothing. H2: against a limited server, more workers buy nothing and queued calls
age into the 3s per-call timeout, so concurrency turns into timeouts. H3: the budget still protects.

Built a TCP proxy in front of the kind API server with two knobs, latency and capacity. It relays
bytes untouched, so TLS stays end to end and the cluster's own CA still verifies — only the timing
changes. Direct call 182ms; through the proxy at 0.3s latency, 521ms.

H1 was wrong by a factor of two: 4.02s and 6 of 30 releases lost, because the two calls per release
are serial, so the added latency lands twice per release. I had counted it once.

H2 was wrong in a more interesting way. With a queue but fast service, eight workers were fine — all
30 reported. With a queue *and* slow service, the numbers went the wrong way: 2 workers reported 8 of
30, 8 workers reported 4, and 16 workers reported **none at all**. Not one read timed out. Throughput
was fixed, and a release's second call sat behind the first call of every other release in flight, so
everything advanced and nothing arrived.

That is day 25's fix behaving as a defect. Concurrency was right for a cluster with spare capacity
and wrong for one without, and no amount of re-reading the code would have shown it.

Fixed by admitting work in waves: start at two, double while a wave completes, stop admitting once
the remaining budget is shorter than the last wave took. `NF_SCRAPE_WORKERS` becomes a ceiling rather
than a target. Overloaded, 30 releases: 6 reported at both 8 and 16 workers, stable across runs, and
the scrape ends early at 2.9s instead of burning the budget. Healthy, 60 releases: 1.92s with all 60
reported, against 2.05s yesterday. Then the whole stack against real Prometheus at 60 releases behind
the slow proxy: target up at 2.9s, six releases whole, and `NFReleaseUnreported` firing for the other
54 **by name** — day 25's alert earning its keep in a case it was not written for.

**Got stuck on:** Writing a test for this honestly. My first version slept in threads — but sleeping
threads are free, so all 30 releases finished and the test proved nothing. Adding a semaphore made it
fixed-throughput but still passed against the old code, because a release completing was one
indivisible step. Modelling two calls per release finally reproduced the shape, and then the test was
flaky both ways: it passed on the old collector about half the time, because which thread grabs the
queue first is a race.

So I stopped trying to assert on how many releases finish — that belongs to the cluster, and it is in
the postmortem with real numbers. The thing this code decides is *how much work it puts in flight*,
and that is deterministic: peak concurrency and releases started. The test asserts those, passes three
times out of three here, and fails three times out of three against main with `assert 16 <= 2`.

Also: I wrote most of the day's code on `main` before noticing I had never made the branch.

**Learned:** A fix is only correct for the conditions it was measured under. Day 25's concurrency was
verified on a cluster with capacity to spare, and the verification was real — it just did not include
the case where the cluster is the bottleneck. Two days later the same code was the reason nothing got
reported.

And when a test refuses to be deterministic, that is usually a sign it is asserting on someone else's
behaviour. The cluster decides how many releases finish; this code decides how much it asks for. The
test got simpler and stronger the moment it asserted only the second.
